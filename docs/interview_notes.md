# Interview Notes

These notes help explain the finished fraud-risk-engine portfolio project in a
plain, interview-ready way.

- What was built: An explainable fraud-risk modelling workflow with data validation, EDA, leakage-aware features, chronological splitting, validation model comparison, validation threshold selection, and one final out-of-time TEST evaluation.
- Why it matters: Fraud detection is imbalanced, so a model can look accurate while missing fraud. The project shows how to evaluate fraud risk with precision, recall, alert burden, and leakage control in mind.
- How it works: `pyproject.toml` defines the package and developer requirements; reusable code lives in `src/fraud_engine/`; scripts reproduce the historical workflows; tests protect the feature, split, threshold, and final-evaluation contracts.
- What is PaySim and why use simulated data? PaySim is simulated transaction data with fraud labels and an existing `isFlaggedFraud` rule. It is useful for portfolio modelling because it provides realistic fraud-detection challenges without using private bank data.
- What does "explainable" mean in this project? It means the model is intentionally simple, uses an auditable 11-feature contract, and can be explained through transparent features, logistic-regression behaviour, and documented threshold trade-offs. It does not yet mean SHAP explanations or automated case narratives.
- Phase 1 adds a safe CSV loader and validation checks so the project can detect invalid transactions before modelling begins.
- The validation step separates hard failures from data-quality warnings, which prevents bad data from silently corrupting later analysis.
- Fraud detection is an imbalanced classification problem: a model can achieve high accuracy by mostly predicting the majority non-fraud class while missing fraud.
- Fraud prevalence is the overall proportion of fraudulent transactions; fraud rate by type is the conditional proportion within each transaction type. A high-volume type and a high-rate type are not necessarily the same.
- Precision measures how many flagged transactions are actually fraud, while recall measures how much fraud the review process catches. Both matter because investigations have limited capacity and false alerts consume analyst time.
- The `isFlaggedFraud` comparison shows what an existing deterministic rule catches and misses; it is a benchmark, not a feature or a replacement for model evaluation.
- EDA is separated from feature engineering and modelling so observed patterns can be documented before choices about transformations, leakage, splits, or algorithms are made.
- Phase 3 intentionally excludes variables that might be predictive but would not be available at scoring time. A feature that improves an offline score through post-transaction information is not a credible production feature; excluding it protects the validity of the fraud-risk system.
- The baseline keeps only amount, origin-side pre-transaction information, simple explainable ratios/indicators, and fixed transaction-type flags. This makes each column easy to describe and audit.
- Phase 4 uses train steps 1-446, validation steps 447-594, and test steps 595-743. Whole steps stay together because the dataset cannot reliably order transactions within a shared step.
- If asked, "Why didn't you use a random train/test split for fraud detection?", I would explain: "The intended use is to score future transactions. A random split could place future patterns in training and make performance look more reliable than it would be operationally. A chronological split tests whether the approach transfers forward in time."
- The row counts are not equal across chronological periods because transaction volume changes over time. The later data also has a higher observed fraud rate, so that temporal distribution shift is preserved rather than corrected away.
- Logistic regression was chosen first because it is interpretable, produces a continuous score, and provides a defensible linear baseline before more complex models.
- Scaling is fitted on training data only so validation and test observations cannot influence the learned feature transformation.
- Class weighting was tested because fraud represents only about `0.129%` overall; it changes the fitting emphasis on rare fraud and can improve recall at the cost of many more false alerts.
- Average Precision was the primary validation metric because it focuses on precision-recall behaviour for rare fraud cases; accuracy would mostly reflect the majority class.
- TEST was not used for preprocessing fitting, model fitting, model selection, threshold selection, or model-performance evaluation before Phase 6B.
- Observed validation results: unweighted logistic regression achieved AP `0.729030`, ROC-AUC `0.984607`, and recall `0.203247` at `0.5`; balanced logistic regression achieved AP `0.692946`, ROC-AUC `0.994853`, and recall `1.000000` but precision `0.133333`.
- If asked, "Why did you choose the unweighted model over the balanced model?", I would explain: "Average Precision was chosen before modelling as the primary ranking metric because fraud is rare. The unweighted model ranked better by that metric. The balanced model had higher ROC-AUC and very high recall at the default threshold, but those did not override the pre-defined AP-primary policy."
- If asked, "How did you choose the classification threshold?", I would explain: "Threshold `0.5` was only a default reference. I compared validation recall operating points and selected the 70% recall point as a project demonstration policy. It captured a substantial majority of validation fraud while keeping the alert rate below 1%. Higher recall levels caused sharply increasing false-positive burden, and I did not invent business cost or analyst-capacity assumptions."
- The selected demonstration threshold is `0.02895689437774259` in machine-readable artifacts, though it may be displayed rounded in documentation. It is not claimed to be optimal, profit-maximising, production-ready, or economically optimal for a real bank.
- If asked, "Why didn't you maximise F1?", I would explain: "F1 weights precision and recall equally. That is a business preference, not a neutral fact, and this project does not have approved costs or review-capacity assumptions to justify it as the objective."
- If asked, "Why didn't you refit on train plus validation?", I would explain: "Refitting would change preprocessing, coefficients, intercept, prevalence, and score distribution, so a validation-selected threshold would no longer map to exactly the same model. Keeping the train-fitted model gives a cleaner final TEST story."
- Thresholds selected on validation can transfer imperfectly to test because fraud prevalence changes over time. In this project, the threshold was transferred unchanged and evaluated once on TEST rather than tuned afterward.
- If asked, "What does sealed test mean here?", I would explain: "Earlier phases documented split-level test row counts and prevalence, so I do not claim test labels were literally never observed anywhere. The important discipline is that TEST was not used to fit preprocessing, fit the model, choose features, select the model, select the threshold, or evaluate model performance before the final Phase 6B run."
- If asked, "What happened after final TEST results?", I would explain: "The model and threshold stayed frozen. The result is final out-of-time evaluation evidence, not another tuning loop."
- If asked, "What were the final TEST results?", I would explain: "On the out-of-time TEST period, the frozen unweighted logistic model achieved Average Precision about `0.780`, ROC-AUC about `0.983`, precision about `72.6%`, recall about `68.7%`, and F1 about `0.706` at the validation-selected threshold."
- If asked, "Did the threshold transfer?", I would explain: "The threshold was chosen for 70% validation recall and transferred unchanged to TEST. TEST recall was about `68.7%`, and precision increased from about `59.5%` on validation to about `72.6%` on TEST, so it transferred reasonably without post-TEST tuning."
- If asked, "Why was TEST Average Precision higher than validation?", I would explain: "Average Precision depends on class prevalence as well as ranking quality. The TEST period has different fraud prevalence, so the higher AP does not prove the model became intrinsically better. ROC-AUC stayed similar, which supports a more cautious interpretation."
- If asked, "How did the model compare with `isFlaggedFraud`?", I would explain: "`isFlaggedFraud` had perfect precision on TEST but detected only 8 of 1,654 frauds, so recall was below `0.5%`. The logistic model detected 1,136 frauds at the frozen threshold, with 429 false positives."
- If asked, "Did you change anything after seeing TEST?", I would explain: "No. The model, features, preprocessing, class weighting, solver, fitting policy, and threshold were frozen before TEST and were not changed after seeing the result."
- If asked, "Why was no model binary committed?", I would explain: "This portfolio emphasizes reproducible code and auditable artifacts rather than shipping a serialized model. The model can be rebuilt from the documented code, raw data, and frozen policy, while avoiding binary artifacts in Git."
- If asked, "What would change in a real bank deployment?", I would explain: "A real deployment would need verified decision-time data availability, privacy and security review, monitoring, governance approvals, analyst workflow design, cost and capacity assumptions, and human review procedures. This portfolio does not claim production readiness."
- If asked, "What monitoring would be needed after deployment?", I would explain: "I would monitor score distributions, feature distributions, fraud prevalence, alert volume, precision and recall after labels mature, data-quality failures, and drift across transaction types and time periods."
- If asked, "What would you do next without rewriting the frozen TEST result?", I would explain: "I would add descriptive explainability, monitoring design, and a lightweight dashboard around the frozen result. Those extensions would explain and present the historical model, not retune it."
- If asked, "What makes this model explainable?", I would explain: "The feature set is small and transparent, feature availability is documented, leakage controls are explicit, logistic-regression coefficient directions can be inspected, and the validation threshold decision is recorded in committed artifacts."
- If asked, "What does a positive logistic-regression coefficient mean?", I would explain: "It means that, within the fitted model and holding other features fixed, higher values of that transformed feature are associated with higher model log-odds of fraud."
- If asked, "Can you compare coefficient sizes directly?", I would explain: "Only carefully. Continuous features were standardized, so their coefficients refer to one-standard-deviation changes. Binary indicators refer to switching from 0 to 1. Correlated features like `amount` and `log1p_amount` also make isolated magnitude comparisons tricky."
- If asked, "If all five transaction types are one-hot encoded, how do you interpret their coefficients?", I would explain: "All five mutually exclusive type indicators are retained in the model, so there is no omitted reference category. I therefore avoid interpreting an individual type coefficient as an effect relative to a baseline category. Instead, differences between the fitted type coefficients show how the model distinguishes categories while holding the other features fixed. The coefficients remain descriptive model parameters, not causal effects."
- If asked, "Are these features causal drivers of fraud?", I would explain: "No. The coefficients describe associations learned by the model on simulated data. They are useful for interpretation, but they are not causal effects."
- If asked, "Why didn't you use SHAP?", I would explain: "For this pass, the final model is already a small logistic regression with 11 transparent features, so direct coefficient interpretation is simpler and faithful to the model. SHAP is useful in many settings, but here it would add complexity without improving the portfolio story much."
- If asked, "What is the key limitation?", I would explain: "PaySim is simulated data and this is a simple 11-feature conservative model built for portfolio evidence. The results show disciplined modelling and evaluation, but they do not imply real-bank production performance."
